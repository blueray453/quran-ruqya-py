data/mulk.json is the dataset, about 486 KB.
data/analysis_report.txt holds the frequencies and the rule accuracies, if you redirect the analysis as above.

To change the annotation, edit annotations/mulk_spec.json and re-run the build. Each phrase is [word_start, word_end, english, bangla]. The build stops with an error if the phrases leave a gap or overlap.

To read the data in Python, load the JSON and walk down the levels. I ran this snippet just now:

import json
J = json.load(open('data/mulk.json', encoding='utf-8'))
for c in J['ayahs'][14]['clauses']:          # ayah 15
    print(c['clause_id'], c['translations']['en'], '|', c['translations']['bn'])

For ayah 15 it prints five lines, for example 67:15:c1 He is the One who | তিনিই যিনি. Every word is at ayah → clause → phrase → word, with its tags and glosses. For example, x['prefix_tags'] gives the prefix tag, and x['is_clause_start'] tells you whether the word begins a clause.

To use jq, these should work, but I couldn’t test them because jq isn’t installed in my sandbox:

jq -r '.ayahs[].clauses[] | "\(.clause_id)\t\(.translations.en)\t\(.translations.bn)"' data/mulk.json

jq '[.ayahs[].clauses[].phrases[]] | group_by(.text_norm) | map(select(length>1) | {text:.[0].text, n:length})' data/mulk.json

The first lists every clause with both translations. The second lists repeated phrases and how often each occurs.

To read the analysis report, the headings are:

=== 1. FREQUENCY lists repeated clauses and phrases, plus translation consistency for each language. In the current data the most repeated phrase is قُلۡ, six times.
=== 2. RULE MINING shows how each tag predicts boundaries, and then the explicit rules with their accuracy, such as 15/15 for the waqf-mark rule.

The same phrase-level and clause-level fields are also what you’d feed into your own analysis. Group by text_norm for repetition, by pattern for structure, or by translation_keys.bn for Bangla consistency.

*Only one file in the whole pipeline needs a language model: `annotations/mulk_spec.json`.* Everything else is regenerated by scripts from that file and the sources.

## Deterministic (scripts, repeatable)

| Step | Why it's deterministic |
|---|---|
| Slicing the QUL files, converting the treebank, fixing the three merged-word ayahs | Pure data transformation |
| Alignment and count checks across QPC, QUL and the treebank | Counting and comparing keys |
| Attaching root, lemma, stem, tags, features, glosses and repetition data to words | Copied from the sources by word key |
| Boundary flags (`is_clause_start`, `boundary_before`, `prev_word_waqf`), `text_norm`, tag patterns | Computed from the spec and the sources |
| Joining phrases into clause and ayah translations | String joining |
| `translation_keys` (lower-casing, punctuation stripping, "and it is" → "and he is") | String normalisation |
| The tiling check, the consistency check, frequencies, rule mining and accuracy | Counting |
| Cross-checks against treebank sentences, PP spans and Mutashabihat | Comparison |

## Needs an LLM, or a person

| Step | Why |
|---|---|
| **Clause and phrase boundaries** | A judgement about which chunks form minimal units that read naturally in English. |
| **English wording per phrase** | It includes choices like reordering inside a phrase, punctuation and quote nesting. |
| **Bangla wording per phrase** | The same choices, plus respectful forms. A Bangla reader should review it. |
| **Resolving disagreements the scripts flag** | Examples are the 67:23:11 sentence break and CONJ versus CIRC. The script finds them but can't decide them. |

## In between

- **Drafting from word glosses.** A script can assemble the QUL glosses for a phrase into a first draft, and the model then polishes it.
- **Translation memory.** The script detects the same Arabic with different English, and a person or the model chooses the fix.

## Why it matters for the whole Quran

- **Scale.** The model-written part is about 49,500 phrases in two languages, and the deterministic part is cheap to re-run whenever the spec changes.
- **Variance.** A model won't split the same text identically on every run. That's why the spec is the saved artifact. Record which model and which conventions produced each ayah, and mark ayahs `draft` or `reviewed`.
- **Circularity.** The model must annotate from the Arabic text and the meaning only. If it saw the tags or the mined rules, the rule statistics would partly measure the model following them.
- **Consistency across surahs.** This is the hardest part, because a model can drift from its earlier choices. The conventions file and worked examples are what keep it steady.
